# 적대적 AI 프로젝트 직무 연계와 인터뷰 가이드

이 문서는 자율운항선박 AI 보안 프로젝트의 구현 증거를 AI 보안, 컴퓨터비전, 모델 검증 및 안전 연구 직무의 언어로 설명하기 위한 포트폴리오 보조자료다. 채용·교육 자료는 설명 구조의 참고자료이며 공격 성능이나 안전효과의 기술적 증거가 아니다.

## 한 문장 정의

이 프로젝트는 선박 10클래스 CNN·MobileNetV2 분류기의 Clean 성능을 재현하고, 명시적 공격 계약 아래 FGSM 취약성을 측정해 모델 인식 오류의 안전영향 연구로 확장하는 실험·감사 프레임워크다.

## 직무 키워드에서 검증 증거까지

| 직무 키워드 | 프로젝트에서 수행한 행동 | 확인 가능한 증거 | 주장하지 않을 내용 |
|---|---|---|---|
| 모델 기준성능 재현 | CNN·MobileNetV2를 동일한 781장 테스트셋에서 평가하고 표본별 산출물 생성 | `docs/CLEAN_BASELINE_RESULTS.md`, `results/clean/` | 학습과정 전체가 완전 재현됐다는 주장 |
| 공격 계약 설계 | FGSM을 true-label untargeted 1-step과 L∞ 제약으로 사전 정의 | `docs/EXPERIMENT_CONTRACT.md`, 공격 구현·테스트 | 반복 공격을 단일 FGSM으로 표현 |
| 공격 무결성 검증 | ε=0 대조조건, [0,1] clipping, L∞≤ε, clean-correct ASR 분모를 검사 | FGSM 테스트·metadata·결과 감사 | 유리한 ε만 선택한 공식 성능 주장 |

| 모델 비교 해석 | Clean accuracy와 공격 후 robust accuracy·ASR을 모델별로 분리 비교 | provisional FGSM 결과·classification report | 높은 clean 성능이 항상 더 취약하다는 인과 일반화 |

| 안전 범위 통제 | 인식 오류→항로판단을 연구용 안전영향 시뮬레이터로만 정의 | `docs/PROJECT_SCOPE.md` | 실제 자율운항 제어·침해·충돌 방지 시스템 구현 |

## 직무별 연결

### AI 보안·Adversarial ML

공격 수식, 위협모델, ε 공간, ASR 분모와 대조조건을 명시하고 변조 탐지 테스트를 구축한 경험을 강조한다. 현재 공식화된 공격 결과와 방어기법 검증이 모두 완료된 것으로 표현하지 않는다.

### 컴퓨터비전·모델 검증

동일 테스트 manifest, 표본별 예측, 클래스별 precision·recall·F1과 confusion matrix를 사용해 모델별 취약 클래스를 분석한 경험을 강조한다. Train/Val 분할과 MobileNet 학습 당시 전처리는 직접 증거가 부족하다는 한계를 함께 말한다.

### 안전·신뢰성 연구

확인된 결과, provisional 결과, 계획을 분리하고 실제 제어시스템이 아닌 연구용 시뮬레이터로 범위를 제한한 판단을 강조한다. 공격 성공률을 실제 사고확률이나 선박 안전성으로 변환하지 않는다.

## 자소서 경험 구성

1. **상황:** 자율운항 인식모델은 clean 정확도만으로 적대적 입력에 대한 신뢰성을 설명할 수 없다.
2. **문제:** 기존 모델·데이터의 학습 이력이 불완전하고 공격 정의가 흔들리면 결과 비교와 재현성이 무너진다.
3. **행동:** Clean baseline을 재현하고 manifest·해시를 고정했으며, FGSM 수식·ε·ASR 분모·대조조건을 사전등록하고 산출물 감사와 mutation test를 구축했다.
4. **결과:** CNN 504/781, MobileNetV2 613/781의 Clean 정분류를 재현했다. 멘토 승인 전 FGSM 결과는 별도 provisional 경로와 문서로 격리했다.
5. **한계:** MobileNet 학습 당시 전처리와 Train/Val 분할은 미확정이며, 가우시안·평균 필터 방어는 experimental 비교 실험으로 구분한다. BIM·PGD·JSMA의 검증 완료나 실제 안전영향 검증을 주장하지 않는다.
6. **향후계획:** ε 범위 승인 후 공식 재실행하고, 공격별 강건성·전이성·방어 trade-off를 사전등록된 조건으로 비교한 뒤 안전영향은 별도 시뮬레이션으로 검증한다.

## 예상 꼬리질문

### 왜 ASR 분모를 전체 표본이 아니라 clean-correct로 잡았나?

원래부터 오분류된 표본은 공격 때문에 실패한 것으로 볼 수 없기 때문이다. CNN은 504장, MobileNetV2는 613장의 clean-correct 표본을 분모로 사용한다.

### ε=0은 왜 필요한가?

공격 파이프라인이 입력이나 예측을 의도치 않게 바꾸지 않는지 확인하는 대조조건이다. clean prediction, accuracy drop, ASR과 L∞가 모두 원상태여야 한다.

### provisional 결과도 자소서에 쓸 수 있나?

구현·검증 경험의 증거로는 사용할 수 있지만 공식 공격 성능처럼 제시하면 안 된다. 반드시 승인 전 예비 결과라는 상태와 재실행 계획을 함께 밝힌다.

### 실제 자율운항선을 공격한 것인가?

아니다. 로컬 선박 이미지 분류모델을 대상으로 한 연구용 white-box 실험이며 실제 선박 네트워크나 제어시스템을 침해하지 않았다.

### 본인의 역할과 AI 에이전트의 역할은 무엇인가?

프로젝트 책임자는 문제·실험 범위, 자료 선별, 로컬 실행, 결과 검토와 통합을 담당했다. Codex·Jules 등 에이전트의 구현·감사 작업은 Git 작성자와 기여 문서로 구분한다.

## 참고 범위

자소서·이력 점검 자료에서는 직무 키워드를 행동과 증거로 연결하고, 상황·문제·행동·결과·한계·향후계획으로 경험을 구성하는 원칙만 참고했다. 강의 예문·표·양식은 복제하지 않으며 기술 성능의 근거로 사용하지 않는다.

## 팀 검토에 적용

상대별 설명, 검토자 온보딩, 피드백 처리와 역할 구분은 [팀 검토와 결과 전달 절차](REVIEW_WORKFLOW.md)를 따른다. 가우시안·평균 필터의 구현·실험 기록은 [평균 필터 실험](experiments/MEAN_DEFENSE_EXPERIMENT.md)과 연결하고, 방어 인지 공격에 대한 한계를 함께 설명한다. 이 직무 소개는 결과의 공식 승격이나 저자 합의를 대신하지 않는다.

## AX 포트폴리오: 주장보다 확인 경로를 먼저 제시

사용자가 제공한 「AX 시대의 포트폴리오 특강」 PDF 6–9, 11–12, 17–20, 31–36, 46–49쪽의 대상 설정·근거 대조·제작 과정 공개 원칙을 참고해 아래 내용을 프로젝트에 맞게 작성했다. 강의의 가상 사례·수치·채용 관련 주장은 프로젝트 실적이나 연구 근거로 옮기지 않는다.

### 첫 30초 설명

> 선박 이미지 AI가 작은 디지털 변형에 얼마나 흔들리는지 측정하고, 간단한 전처리 방어의 효과와 한계를 같은 조건에서 비교합니다. 결과는 표본별 기록과 감사 코드로 추적할 수 있습니다.

바로 이어서 “정해진 이미지 분류 실험이며 실제 운항·충돌 위험 검증은 아닙니다”를 함께 설명한다. MARIS의 3D 크기나 디자인 완성도를 모델 성능의 증거로 사용하지 않는다.

### 개인 기여를 설명하는 네 항목

1. **사람이 결정한 범위:** 실제 합의 기록이 있는 연구 대상·비교 조건·결과 채택 범위를 설명한다. 최희찬을 팀장으로 기재하지 않는다.
2. **AI에게 맡긴 작업:** 코드·문서 초안·감사 보조 등 실제 수행 내용을 작성자·커밋으로 확인한다. 타인의 구현을 본인의 독립 구현으로 바꾸지 않는다.
3. **검토 후 바꾼 내용:** 해당 PR·diff·회신 근거가 있는 변경만 기록한다. 오류 발견자가 확인되지 않으면 개인의 성과로 귀속하지 않는다.
4. **남은 한계:** provisional/experimental 상태, 원본 모델·이미지 접근 요건, 반복 공격·현장 검증 미수행을 함께 남긴다.

### 공개 문구 검토 프롬프트

> 지정한 원고 버전 또는 웹 코드 커밋을 읽고 주장 목록을 먼저 작성하세요. 각 주장에 근거 파일·조건·분모·예비/실험 상태·한계를 연결하세요. 근거가 없으면 미확인으로 표시하고 수치나 개인 기여를 만들지 마세요. 수치는 canonical CSV/JSON과 기존 감사 정의로 대조하세요. 수정 제안은 관측 사실과 해석을 나누어 제시하고, 승인된 범위의 문구만 변경하세요. 실제 확인한 화면 폭·브라우저·실기기 여부도 구분하세요.

웹 적용을 검토할 때에는 수치 옆의 조건·한계, 클릭 가능한 근거, 성공/실패 사례의 균형을 먼저 확인한다. 이 문서 변경은 MARIS 배포 완료 또는 실제 사용자 이해도 검증을 의미하지 않는다.

## 전자·반도체 직무로 연결할 때의 경계

추가 참고는 「한국공학대학교 전자, 반도체 공학 전공자 취업 강의」(털보아저씨) PDF 39–43, 46쪽의 직무 관련성·구체적 행동·설명 가능한 경험 원칙과, 「생성형 AI를 활용한 입사지원서 준비 전략」(유재천) PDF 82–90쪽의 목적/업무/역량 분석 및 행동의 이유를 설명하는 방식이다. 원문·그림·지원서 예문은 복제하지 않는다. 강의의 채용 전망·연령 기준·기업 사례를 현재 채용 사실로 사용하지 않는다.

이 프로젝트의 직접 증거는 해양 이미지 분류기의 평가·감사·결과 전달이다. 반도체 지원 시에는 아래와 같이 전이 가능한 작업 방식을 설명한다. 반도체 공정·설비·제품 검증을 실제 수행한 경력으로 바꾸지 않는다.

| 연결할 역량 | 이 프로젝트에서 제시할 행동·근거 | 별도로 필요한 경험 또는 금지할 주장 |
|---|---|---|
| 조건을 통제한 비교 | 동일 manifest·모델에서 공격 조건과 필터별 결과 비교; 실험계약·표본 CSV | 반도체 공정 레시피 최적화나 수율 향상을 수행했다는 주장 금지 |
| 이상 결과의 원인 점검 | 입력 해시·ASR 분모·정상 손실·공격 계약을 나누어 확인; 감사 코드·실제 실패 로그 | 선박 이미지 오분류를 웨이퍼 결함이나 장비 고장 진단으로 동일시하지 않음 |
| 변경 후 회귀 확인 | 변경 파일·테스트 범위·source SHA를 연결; PR·테스트 기록 | pytest 통과를 제품 신뢰성 인증·JEDEC 평가·양산 검증으로 표현하지 않음 |
| 재현 가능한 인수인계 | run ID·근거 경로·미확인 사항을 다음 검토자에게 전달 | 현장 MES/FDC 운영 또는 실제 생산라인 도입 경험은 별도 증거 필요 |

### 지원 공고에 맞춘 경험 정리

기업·직무가 정해지면 현재 공식 공고의 URL과 확인일을 먼저 기록한다. 다음 순서로 한 경험만 작성한다.

1. **목적:** 그 직무가 해결하려는 문제와 이 프로젝트 경험이 연결되는 이유.
2. **실제 업무:** 본인이 맡아 실행·검토한 일과 팀원·AI가 수행한 일을 분리.
3. **행동의 이유와 과정:** 왜 해당 조건/분모/검사를 확인했는지, 어떤 순서로 대조했는지, 불일치에 어떻게 대응했는지.
4. **결과와 한계:** 검증 시점의 커밋·로그·수치 출처를 붙인다. 향상되지 않은 결과도 보존하며 산업 현장 적용 여부를 명시한다.

위 항목은 기록 틀이며 개인이 전부 수행했다는 진술이 아니다. 실제 PR·로그·팀 확인이 없는 항목은 비워 둔다. 성능 수치를 쓸 때 기존 canonical 근거에서 계산하고, 팀 전체 성과를 개인 구현 실적으로 전환하지 않는다.

### 면접 전에 답할 질문

- 정상 정확도가 높은 모델이 공격에도 강하다고 말할 수 있는가? 어떤 조건의 결과로 답하는가?
- 방어가 정상 이미지까지 바꿀 때 무엇을 비용으로 보고했는가?
- 감사 PASS가 실제 모델 재추론이나 현장 안전성 검증을 대신하지 못하는 이유는 무엇인가?
- 본인이 직접 결정·실행·확인한 항목과 AI·팀원의 기여를 어떤 기록으로 구분하는가?
- 이 경험을 반도체 업무에 옮길 때 추가로 필요한 도메인 지식·데이터·현장 검증은 무엇인가?

취업 자료의 역할은 경험을 정확하게 설명하는 데 한정한다. 이를 이유로 논문에 반도체 성능 주장이나 새 데이터·기능을 추가하지 않는다.
