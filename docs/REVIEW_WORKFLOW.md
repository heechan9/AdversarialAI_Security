# 팀 검토와 결과 전달 절차

이 문서는 연구 결과를 추가하는 실험계약이 아니라, 기존 근거를 이해하고 검토 의견을 반영하는 협업 절차다. 2026-09-19 작성. 실제 담당·일정은 팀장이 팀원과 합의한다.

## 적용 근거와 중복 방지

사용자가 제공한 렛유인에듀·한국공학대학교 「전공 특강(영업관리, HRD)」, Leo, 파일명 날짜 260914, PDF 페이지 기준:

| 참고 개념 | 자료 위치 | 이 프로젝트에서 적용 |
|---|---|---|
| 상대 중심 설명과 제안 근거 | 28–30쪽 | 독자마다 먼저 답할 질문과 근거를 구분 |
| 데이터의 맥락 해석 | 31–34쪽 | 정확도뿐 아니라 조건·분모·정상 손실을 함께 확인 |
| 시간·자원 우선순위 | 39–41쪽 | 제출 차단 문제를 기능 확장보다 먼저 해결 |
| 피드백과 후속 조치 | 44–46쪽 | 의견을 변경 파일·재검토 결과까지 연결 |
| ADDIE와 PDCA | 92–93쪽 | 요구 파악→자료 준비→검토→수정→재확인 |
| 온보딩과 역할별 학습 | 94–96쪽 | 새 검토자에게 작은 과제와 완료 기준 제공 |

위 내용은 강의에서 착안한 프로젝트 운영 방식이다. 교육 효과나 모델 안전성이 검증됐다는 의미가 아니다. 강의 원본·그림·예문은 저장소에 재배포하지 않는다. 기존 [재현성](REPRODUCIBILITY.md), [독립 검증](INDEPENDENT_VERIFICATION.md), [직무 설명](ROLE_ALIGNMENT.md)을 재사용하며 별도 성능 지표나 승인 체계를 만들지 않는다.

## 독자별 첫 질문

| 독자 | 먼저 전달할 내용 | 확인 자료와 경계 |
|---|---|---|
| 비전공 관람자 | 같은 이미지에 작은 디지털 변화를 주면 모델 판단이 달라질 수 있다 | MARIS의 성공·실패 사례와 전체 결과. 저장 기록 재생이며 3D는 설명용 |
| 팀원·멘토 | 이 결론이 어느 조건에서 성립하고 어떤 한계가 있는가 | 원고 버전, 공격 계약, 방어 정상 성능·전달/방어 인지 조건, 미결정 항목 |
| 재현 검토자 | 동일 산출물에서 같은 수치를 계산할 수 있는가 | source SHA, manifest, 표본 CSV, 감사 명령·종료 코드. CSV 재계산과 모델 재추론 구분 |
| 향후 현업 검토자 | 실제 영상 환경에 적용하려면 무엇이 더 필요한가 | 실제 카메라·환경 변화·센서/제어 검증은 후속 연구. 현장 도입 수요·사고 감소 효과는 미검증 |

정확도는 전체 평가 표본, ASR은 해당 평가 파이프라인의 정상 정답 표본을 분모로 설명한다. 방어 적용 전후 ASR 분모가 다를 수 있으므로 비율만으로 방어 우열을 말하지 않는다. 구체적 수치는 기존 CSV/JSON과 감사 출력에서 가져오며 이 문서에 별도 정답으로 복제하지 않는다.

## 검토자 온보딩: 한 과제로 시작

1. [연구 범위](PROJECT_SCOPE.md), [공격 계약](EXPERIMENT_CONTRACT.md)을 읽고 실험 대상과 미검증 대상을 구분한다.
2. [가우시안 방어](GAUSSIAN_DEFENSE.md), [평균 필터 실험](experiments/MEAN_DEFENSE_EXPERIMENT.md)에서 전달 공격과 방어 인지 공격을 구분한다.
3. 자신이 맡은 표 한 개 또는 이미지 한 장만 근거와 대조한다. 원본 CSV를 수정하지 않고 별도 [회신 양식](templates/review_feedback.csv)에 기록한다.
4. 근거 위치를 모르면 `미확인`으로 남긴다. 원본 이미지 없이 선종을 확정하거나, AI 설명을 사람의 관찰로 바꾸어 쓰지 않는다.
5. 아래 세 질문을 자신의 말로 설명하고 검토 상대가 오해 여부를 확인한다. 이 확인은 내부 이해 점검이며 교육 효과 연구가 아니다.

- ASR이 실제 선박 사고 확률이 아닌 이유는 무엇인가?
- 기존 공격 이미지를 필터로 처리하는 것과 필터까지 고려해 공격을 만드는 것은 어떻게 다른가?
- CSV 정합성 감사와 원본 이미지·모델로 다시 추론하는 검증은 어떻게 다른가?

시각 검토는 `설명 확인`과 `선종 판정`을 별도 항목으로 기록한다. 설명 확인을 라벨 정확성으로 집계하지 않는다. 31장·32장 분할 검토를 독립 이중 검토로 표현하지 않는다. 세부 판정은 [시각 검토 감사](VISUAL_REVIEW_AUDIT.md)를 따른다.

## 역할과 전달 경로

- 팀장 김태희: 팀 의견 취합, 멘토 검토 요청과 회의 일정 조율, 제출 관련 합의 정리.
- 팀원 최희찬: 기술 구현·실험 근거·원고 수정 지원. 팀장이나 멘토 승인자로 대신 기록하지 않는다.
- 김기호·이재혁을 포함한 검토 참여자: 합의한 문서/이미지 범위를 확인하고 직접 수행한 작업과 사용한 보조도구를 기록한다. 추가 과제가 자동 배정된 것은 아니다.
- Codex·Jules 등 도구/에이전트의 작업과 사람의 검토를 구분한다. 실제 기여는 [CONTRIBUTIONS.md](../CONTRIBUTIONS.md)의 증거 원칙을 따른다.

팀장과 팀원의 동의, 멘토의 의견, 코드 병합, 결과 공식 승격은 각각 별개 기록이다. 이 절차로 기존 승인 필드나 실험 상태를 변경하지 않는다.

## 검토 요청 → 수정 → 재확인

검토 요청에는 `원고 버전 / source SHA 또는 run ID / 대상 표·파일 / 답변이 필요한 질문 / 합의한 기한`을 적는다. 회신 양식은 기존 연구 CSV와 분리된 업무 기록이며 모델 성능 자료가 아니다. 실제 회신을 받을 때 새 사본에 작성하고 완료를 미리 채우지 않는다.

상태는 `접수 → 검토중 → 수정완료 → 재확인완료`로 진행한다. 변경하지 않으면 `보류` 또는 `미반영`과 이유를 기록한다. 완료하려면 변경 위치와 확인자가 모두 있어야 한다. 의견 수나 커밋 수로 기여도·저자 순서를 자동 산정하지 않는다.

| 우선순위 | 처리 대상 | 완료 기준 |
|---|---|---|
| 제출 전 필수 | 표·본문 수치 불일치, 분모·출처 누락, 예비/실험 상태 오표기, 선종 판정 의미 혼동, 저자/양식 미확정 | 근거 대조 및 팀 재확인; 양식·저자 정보는 실제 확정 기록 |
| 검토 중 보완 | 전문용어 풀이, 표·그림 가독성, 성공/실패 설명 균형 | 수정 위치와 검토자 확인 기록 |
| 후속 연구 | 새 공격·데이터·센서 융합·실제 운항 검증 | 별도 범위·자원·실험계약 합의 전에는 완료 목록에 넣지 않음 |

검토 묶음을 보낼 때 미해결 필수 항목과 다음 담당을 함께 전달한다. 제출 목표일과 멘토회의 일시는 팀장이 실제 공지·참석 가능 시간을 확인해 정한다. 여기에는 확인되지 않은 일정이나 완료율을 기입하지 않는다.

## 재사용할 요청문 틀

> [검토자]님, [버전/커밋]의 [표·문단·이미지] 확인 부탁드립니다. [질문]에 대해 [근거 파일/행]을 함께 남겨주세요. 확인이 어려우면 미확인으로 적어주셔도 됩니다. 원본은 수정하지 말고 회신 양식 사본에 기록해주세요. [합의한 기한]까지 가능하신지 알려주세요.

## 최종 전달 체크

- [ ] 원고·근거·검토 의견이 같은 버전을 가리킨다.
- [ ] FGSM provisional과 방어 experimental 표기를 유지한다.
- [ ] 방어의 정상 성능 비용과 방어 인지 공격 조건을 함께 설명한다.
- [ ] MARIS는 저장된 결과 재생이며 설명용 3D가 실제 선박/제어 실험으로 읽히지 않는다.
- [ ] 해외 자료는 배경/후속 과제이며 외부 성능검증으로 주장하지 않는다.
- [ ] 실험 사실·사람 판단·AI 보조·미확인을 구분했다.
- [ ] 미해결 의견, 저자 정보와 멘토 검토 일정을 팀장이 확인한다.

## AX 자료를 반영한 검토 완료 기준

추가 참고: 「AX 시대의 포트폴리오 특강」 PDF 11–12, 31–36, 46–49쪽. 강의의 가상 인물과 사례는 재사용하지 않는다.

검토자는 첫 설명에서 연구 대상·확인 방법·범위 한계를 찾을 수 있어야 한다. 공개 문구는 주장 → 근거 → 조건/분모 → 한계 순으로 확인한다. 사람이 결정한 내용, AI 구현, 확인된 수정, 남은 한계를 구분하는 [포트폴리오 안내](ROLE_ALIGNMENT.md#ax-포트폴리오-주장보다-확인-경로를-먼저-제시)를 함께 사용한다. 첫 30초 전달력은 앞으로 사람에게 확인할 항목이며 이미 측정한 성과로 기재하지 않는다.
